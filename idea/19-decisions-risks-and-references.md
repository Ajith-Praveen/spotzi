# 19 — Design decisions, risks, and references

## Architecture decision records

| ID | Decision | Reason | Revisit when |
|---|---|---|---|
| ADR-01 | Synthetic-only input, generated by default | Required scope and reproducible evaluation | A separately authorized future project changes scope |
| ADR-02 | Human approval for investigation decisions | User requirement; preserves accountability | Never remove within this prototype |
| ADR-03 | Modular monolith plus worker | Keeps one end-to-end flow tractable | Measured isolation or scale requirements justify services |
| ADR-04 | PostgreSQL plus Parquet | Transactional cases and reproducible analytics have different needs | Measured storage/compute bottleneck |
| ADR-05 | Rules + anomaly + graph | Complementary explicit, statistical, and relational signals | Ablation shows a component adds no value |
| ADR-06 | Logistic hazard baseline before XGBoost | Defined targets and valid evaluation precede complexity | Challenger passes release gates |
| ADR-07 | NetworkX before graph database | Bounded synthetic graph needs modest infrastructure | Graph volume/query demands exceed measured limits |
| ADR-08 | Deterministic brief first | Reliable citations, offline behavior, lower complexity | Optional rewriting measurably improves readability safely |
| ADR-09 | Case-level queue and distinct-dollar accounting | Reduces repeated work without inflated financial claims | Policy changes with reviewed evidence |
| ADR-10 | No automatic retraining/promotion | Prevents silent drift and feedback loops | Remains human-approved even if training is automated |

## Risk register

| Risk | Why it matters | Mitigation and residual limitation |
|---|---|---|
| Simulation shortcuts | Model memorizes planted artifacts | Multiple seeds, held-out variants, ID randomization; reality still unvalidated |
| Weak clinical context | High legitimate utilization looks suspicious | Contextual peers, exceptions, abstention, human record review |
| Label selection bias | Reviewed cases differ from all cases | Keep selection metadata and unresolved labels; evaluate hidden truth separately |
| Future leakage | Performance becomes misleading | Knowledge-time joins, purged windows, independent calibration |
| Money inflation | Reversals and overlapping cases overstate value | Signed ledger and unique-line portfolio accounting |
| Graph guilt by association | Legitimate connected entities are implicated | Typed evidence, benign networks, bystander metrics, human scope acceptance |
| Automation bias | Reviewer accepts a score uncritically | Source-first views, alternatives, reasoned decision, independent approval |
| Misread probability | Index treated as likelihood | Distinct schema/UI fields and clear target definitions |
| Forecast censoring | Incomplete follow-up mislabeled negative | Eligibility and maturity windows; disclose selection effects |
| False provenance | Uploaded real records labeled synthetic | Bundled-only shared demo; human provenance review for optional imports |
| Rule policy mismatch | Demo rules mistaken for payer policy | Synthetic code namespace and explicit version/applicability |
| Untrusted narrative | Notes or LLM output create unsupported facts | Structured facts, validation, safe rendering, deterministic fallback |

## Assumptions to keep visible

US payer terminology and USD are used because the statement references SIU and claim families typical of that context. This is a design assumption, not a jurisdictional compliance claim. The fictional policies do not implement all Medicare, Medicaid, or commercial payer rules.

The initial forecast grain is provider, not individual member or whole network. Historical outcomes are simulated and availability-dated. Queue hour estimates and score weights begin as configurable assumptions. All final decisions remain human.

| Gross implicated exposure | Unique paid dollars within the proposed review scope |
| Potential excess | Estimated overlapping/improper amount where calculation is supported |

## Completion boundary

These documents provide a concrete build specification, not software, training results, clinical validation, or operational approval. During implementation, replace proposed settings with reviewed configurations and measured reports while preserving synthetic-only data and human decision authority.
